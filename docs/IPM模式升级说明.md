# IPM 模式升级说明

日期：2026-09-28。

## 操作流程

1. 选择「IPM 模式」，连接 MQTT，填写正整数网关 ID 并订阅上行主题。
2. 选择网关、倾角定位同步或 MCU 升级。网关刷新使用基础版本查询，终端刷新按钮为「刷新倾角定位同步」。
3. 网关在 PATCH 中心通过「导入已有 Patch」导入完整 `.bin`；同步端在 PATCH 中心生成或导入带 `.json` 清单的差分包。
4. MCU 先在升级任务页选择「倾角定位-MCU升级」，再在 PATCH 中心通过原有「导入已有 Patch」按钮导入完整 `.bin`；无需提供 `.ipm.json`，也不需要填写 MCU 专用字段。目前跳过 MCU 版本自动识别，导入后显示「版本未知」。
5. 当前选「无 uboot 验证模式」：新导入的 MCU 包可以发布；在原有「旧版本／新版本」位置填写不同的 1～254 整数，再加入正向单次队列。此模式仅验证传输、存储和校验，完成后由测试固件取消；不能当作实际升级成功，也不支持自动反向或循环。当前测试固件实际版本为 1 时，可按固件联调文档填写旧版本 1、新版本 2。
6. 加入升级任务队列，配置 HTTP 或 SFTP 发布。执行前核对实际 HTTP 下载文件的 MD5，再发送升级请求。

「正式模式」要求可验证的 MCU 固件版本及 `0x08008000` APP 向量，拒绝未知版本发布与手填联调版本；正式包和下载联调包不能跨模式进入任务。当前 MCU bin 尚无内嵌版本标识，从 PATCH 中心导入时仍记作未知，因此暂不能在正式模式下创建 MCU 升级任务。待固件提供版本标识后接入自动解析与实际启动后版本核验，方可执行正式测试。手填值只记录为下载联调元数据，不冒充镜像内嵌版本。

IPM 设置、已选设备、包目录、历史和报告按模式隔离；两种 MCU 验证模式也保存在 IPM 工作区和队列项中。切换网关会清除旧目标。活动任务期间禁止切换模式或网关。默认 IPM 包目录为原 HTTP 根目录下的 `IPM` 子目录；也可自定义目录。导入保留原文件名，不额外添加模式前缀；只有同名不同内容时才沿用哈希后缀避让。

## 包校验和项目归属

| 类型 | 传输类型 | 文件要求 |
|---|---|---|
| 网关 | `gateway / type=0` | 含有效类型和版本标识的完整镜像 |
| 同步端 | `iote / type=1` | 经还原验证的同步端差分包，门限 52 KiB |
| MCU | `ex_mcu / type=0` | 8～229376 字节，最大 224 KiB 的完整 APP |

IPM 的可配置门限只显示网关（默认 2 MiB）和同步端（默认 52 KiB）。MCU 完整 APP 固定上限 224 KiB，不作为 Patch 门限显示。

MCU 栈地址必须大于 `0x20000000`、不超过 `0x20008000` 且 8 字节对齐；复位入口须带 Thumb 位，地址位于当前 APP 镜像范围。不能使用包含前 32 KiB 引导程序的整片镜像，也不能用 ELF、HEX 或差分包冒充完整 APP。

当前 MCU bin 尚无内嵌版本标识，按要求暂时跳过自动识别，不读取外部构建归档代替，也不猜测版本。导入阶段只检查文件类型和长度、计算哈希；链接地址与版本保留未知。执行升级时仍要求有效的 1～254 整数版本以及向量、链接地址校验，未知字段不能用默认值绕过。

明确标记为下载联调的包兼容 `0x08000000` 直启镜像与 `0x08008000` 正式 APP 镜像，仍校验长度、哈希、SRAM 栈、Thumb 位和入口范围。普通正式升级仍只接受 `0x08008000`。联调不推进队列的预计运行版本，不写入实际版本缓存，不将下载成功解释为启动新版本成功。

工具在输出目录自动保存项目和文件哈希记录，用于模式隔离及重新加载，不要求用户提供或维护此记录。待识别 MCU 包的记录中版本和地址为 0，仅表示未知，不能作为协议版本。同步差分包继续沿用现有 `.json` 差分清单流程。

## 目标、版本和状态

- 发现只使用 `cmd=3 / auth_list`，聚合多条响应并去重，IPM 仅保留类型 2。不会发送异步状态或节点业务查询。
- 同步版本来自鉴权表；MCU 设备当前版本显示未知，不能用同步版本代替。临时下载联调使用手填实际旧版本，设备在清单阶段执行真实版本匹配；正式版本对仍来自所选镜像。
- MCU 任务固定显式目标。同步支持定向 `range=1` 和广播 `range=0`，广播不发送 `targets`。队列预检记录广播匹配快照，超过 16 个匹配目标时拒绝启动。
- 当前网关没有 `cmd=10` 受理应答。IPM 启动后直接用 `cmd=8/9` 绑定原任务序号和网关 SID；仅明确 `TASK_NOT_FOUND` 时保持同序号、同参数重发，最多三次。查询超时不会重发启动。
- 传输字节达到文件大小、READY、COMMIT、BOOT_VERIFY 或 `cmd=6` 成功提示都不能单独判定成功；继续等待匹配会话的最终状态。
- 请求取消不等于设备立即停止写入。工具保留活动状态查询，区分队列停止与设备最终结果；已提交任务仍可能完成升级。
- 暂无独立 MCU 业务版本查询。日志分析显示已解析证据，并标注缺少 MCU 阶段解析，不把未知阶段作为 MCU 成功证据。

## 验证与实板前置条件

```powershell
dotnet build OtaTool.sln --no-restore
dotnet run --project tests/OtaTool.Core.SmokeTests --no-restore
dotnet run --project tests/OtaTool.App.SmokeTests --no-restore
```

模拟验证覆盖镜像边界、向量和哈希、协议编码、非法目标、无受理应答、幂等重发、错误网关与 SID 隔离、取消竞争、三模式工作区、MCU 版本语义和循环完整包绑定。

本次未连接真实网关或终端，未修改固件。对接说明所列固件仍需完成 MCU OTA 启用、APP 链接及向量迁移、引导搬运、掉电恢复和新 APP 版本确认验收，才能开展实际 MCU 升级。
