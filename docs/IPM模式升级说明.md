# IPM 模式升级说明

更新日期：2026-10-13；适用工具版本：v0.2.9。

## MCU 操作流程

1. 选择 IPM，连接 MQTT，填写网关 ID 并订阅上行主题；选择「倾角定位-MCU升级」。MCU 固定正式流程，没有无 UBoot 模式或手填版本。
2. 在 PATCH 中心「导入升级文件」中导入正常构建的 `rtthread.bin`，也可从 A/B 入口直接导入当前、目标两份完整固件。导入会自动识别 MCU 并选择对应任务。工具读取偏移 `0x8000` 的 APP 信息头，识别版本与设备型号，原样复制完整文件，不提取、不删减、不重新封装。
3. 正向镜像选择目标版本，反向镜像选择设备当前版本，自动生成旧/新版本对。这里保留软件版本一致性检查，只统一烧录和 OTA 的文件格式。
4. 刷新倾角定位同步并选择实际 WIoTa 应用 ID；MCU 采用 1～16 个显式目标，设备型号标识不是目标 ID。
5. 发布完整 BIN 或启动本地 HTTP Range 服务，加入正向、反向或循环队列。实际下载长度、MD5、SHA256、CRC32 都对应完整文件。
6. APP 下载整包并校验，READY 等待网关 COMMIT；重启后 UBoot 从外部包的 `0x8000` 开始搬运 APP，前 32 KiB 的设备 UBoot 保持不变。UBoot 只能通过烧录器烧录更新。
7. 等待同一会话 `cmd=9` 最终成功。字节完成、READY、COMMIT、BOOT_VERIFY 或 `cmd=6` 提示不能单独判定完成。

首次迁移需要使用烧录器安装本次完整基线，UBoot 应显示 v0.2、引导 API 为 2。旧版仅 APP 升级器不支持新整包；后续 OTA 不更新 UBoot。若 APP 要求更高引导 API，应先通过烧录器更新 UBoot。

不要求用户提供 `.ipm.json`，工具仅在自己的包目录生成项目/哈希记录，不修改源文件。同名不同内容通过哈希后缀避让。旧 APP-only 文件和对应队列需用完整固件重新导入；旧 MCU 模式字段会忽略，后续保存不再写入。

## 镜像规则

三工程均在完整 BIN 偏移 `0x9F00` 保存大写 `[IPM][type][version]`：网关=8、WIoTa=2、MCU=3，类型和版本各一字节。MCU 额外保留 `0x8000` 安全头，其版本必须与统一标识一致。WIoTa 制作差分包，网关和 MCU 使用完整 BIN。旧 IPM 镜像不回退按 ECO 解析，需要重新构建；详细规则见 [镜像内嵌版本识别规则](IPM镜像内嵌版本识别规则.md)。

IPM WIoTa Patch 前缀在 v0.2.9 中为 `ipm-wiota`，例如 `ipm-wiota-v1-to-v2-jpwang.patch`。新差分清单明确记录 IPM 模式；其他模式导入会拒绝。EcoLink 和传统模式继续使用各自已有命名规则。已有旧名称包不自动重命名，需新名称时重新制作。

完整 BIN 长度 40960～262144 字节；新 APP 段 8192～229376 字节。完整文件前 `0x8000` 是 UBoot 与 FF 填充，APP 安全头在 `0x8000`，向量在 `0x8200`，统一身份在 `0x9F00`，正文代码从 `0xA000` 开始。

| APP 信息字段 | 完整 BIN 偏移 | 规则 |
|---|---|---|
| 魔数 | `0x8000` | ASCII IPMAPP01 |
| 格式 / 头长度 | `0x8008` / `0x800A` | 1 / 64，小端整数 |
| 软件版本 | `0x800C` | 1～254 |
| 设备标识 | `0x8010` | 16 字节，IPM_GD32L233 后补零 |
| APP 地址 / 向量偏移 | `0x8020` / `0x8024` | 0x08008000 / 0x200 |
| APP 长度 | `0x8028` | 完整文件长度减 0x8000 |
| APP 数据 CRC32 | `0x802C` | 文件从 0x8040 到末尾 |
| 硬件版本 / 最小引导 API | `0x8030` / `0x8032` | 硬件 1，API 1～2；当前构建要求 2 |
| flags / reserved | `0x8034` / `0x8038` | 0 / 0 |
| 头 CRC32 | `0x803C` | 文件区间 [0x8000,0x803C) |

CRC32 为 IEEE/ZIP。整包 CRC32 覆盖文件全部字节，包括包内 UBoot；它与 APP 数据 CRC 是不同用途。信息头后到 `0x8200` 必须填 FF。两组向量均检查 RAM 栈范围/8 字节对齐、Thumb 位和入口范围。UBoot 向量检查只确认文件格式，不授权安装包内 UBoot。

## 包、目标和终态

「系统设置 → 升级前检查」显示 MCU 完整镜像门限：固定 256 KiB（262144 字节），包含 UBoot、填充区和 APP，超过门限会拒绝导入或启动升级。该门限与 MCU 内部 Flash 容量一致，只读且仅在 IPM 模式显示；EcoLink 和传统模式的门限保持各自原有规则。APP 段最大 224 KiB，OTA 仅更新 APP。

| 类型 | 协议 | 文件 |
|---|---|---|
| 网关 | gateway / type=0 | 带类型与版本的完整固件 |
| 同步 | iote / type=1 | 带 JSON 清单并验证还原的差分包，默认 52 KiB |
| MCU | ex_mcu / type=0 | 正常完整 rtthread.bin，最大 256 KiB |

IPM 鉴权列表只保留类型 2，返回的是同步端版本，不能代替 MCU 版本。暂无独立 MCU 版本查询，工具以当前会话 cmd=9 最终成功推进运行版本缓存。当前 IPM 不依赖 cmd=10；仅明确 TASK_NOT_FOUND 时同序号同参数重发，查询超时不重发启动。

IPM 倾角定位同步广播使用 `range=0`，请求中不携带目标 ID；加入队列、整队预检和执行前实时校验均不要求鉴权列表中存在在线且旧版本匹配的同步端。若预检时有可用鉴权快照，升级后逐台复查这些目标的版本；若快照为空，只能以本次任务 `cmd=9` 最终成功状态确认，报告明确说明未逐台复查。定向同步升级仍要求目标出现在当前鉴权列表且起始版本匹配。

工作区、包、设备、报告与其他模式隔离；活动任务期间禁止切换工作区或网关。取消不等于设备立即停止，仍核对最终结果。

从 v0.2.9 起，IPM MCU 不再把 30 分钟当作整次升级总时限。工具仅在同网关、同任务、同 SID 的合法 cmd=9 中观察到传输字节增长或已知阶段向前推进时，刷新无进度等待窗口；默认连续 30 分钟无有效进度时超时，整个任务最多等待 24 小时。重复 RUNNING 状态、不断增长的耗时、错误 SID 和越界字节数不刷新窗口。网关 `timeout_s` 仍为原下游执行预算，单次、循环和队列均由同一监视器判定 MCU 超时；其他模式保持原总时限。

MCU 达到 100%、READY、COMMIT、BOOT_VERIFY 或收到 cmd=6 提示均不直接判定成功。最终仍等待同会话 cmd=9 成功。工具超时只说明没有闭环证据，设备可能继续执行；排查方法见 [MCU 升级成功但工具超时](IPM_MCU升级成功但工具超时.md)。
