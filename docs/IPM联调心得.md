# IPM OTA 工具联调心得

## 先区分三个身份

MQTT 初始升级主题序号是 `task_seq`，每次状态查询产生新的 `query_seq`，网关分配 `session_id`。重发启动保留初始请求和全部参数。只有明确查询不到任务才能重发，查询超时只是状态未知。

## 用会话终态判断升级完成

首轮广播字节发送完毕不代表 MCU 已持久化或新 APP 已启动。补包、Flash 写入、提交和重启核验可能继续很久。模拟器应主动构造 `COMMIT`、`BOOT_VERIFY`、错 SID、错网关以及 `cmd=6` 成功提示，确认工具仍等待当前会话最终状态。

## 独立验证完整镜像

MCU 暂无内嵌版本标识，导入先保存文件长度与哈希；MD5 用于实际下载验证，SHA256 用于防止包替换。无 uboot 下载联调在原有旧、新版本栏手填整数，在加入任务时校验 SRAM 栈地址、Thumb 位和入口范围，允许测试固件支持的直启或正式 APP 向量范围。手填值明确记录为联调参数，不冒充内嵌版本。正式升级仍校验 0x08008000 APP，正反向循环需要两个完整镜像。

## 不混淆版本来源

鉴权表返回同步端版本，不是 MCU 版本。首次 MCU 旧版本来自受控部署信息；后续版本仅接受同会话成功事实。日志阶段解析缺失时显示证据不足，不能把日志评分当成升级成功。

无 uboot 下载联调完成后由固件取消，不改变运行版本。因此不更新实际版本缓存，不自动反向，也不把 READY、取消或测试目标版本作为实际升级成功。工具应把「无 uboot 验证模式／正式模式」写入工作区、队列项和最终任务；包导入、发布和执行各层都要核对模式与联调标记，避免切换界面后旧队列绕过门禁。正式模式当前因 MCU 镜像无内嵌版本而阻止未知版本进入任务，待固件提供标识后接入自动识别。

## 检查选择与日志的完整路径

新增任务类型时不仅要更换显示名，还要覆盖设备勾选回调。IPM 的同步与 MCU 类型曾漏在选择同步分支之外，导致界面已勾选但固定目标列表为空。回归应实际切换勾选状态并检查任务中的目标 ID。

状态栏和日志曾使用不同的文案入口：状态 getter 已替换模式名称，但日志直接写入原字符串。写日志时也需应用模式文案转换，并兼容已缓存的日志显示；模式切换按钮名称按用户要求始终为 EcoLink 模式。

## 历史报告按模式查询

报告表已有模式字段，仅在界面加载完成后筛选仍可能出错：切换模式时，旧模式的异步查询晚返回会覆盖新模式列表。应在 SQL 中先按 `mode` 筛选再排序截断，并给每次界面加载分配序号；模式或归档范围变化后，过期结果不得写回。切换时立即清空旧列表和多选状态，避免用户在新模式下操作旧报告。单任务与测试计划报告都要覆盖此规则。

## 推荐回归方式

核心层使用模拟 MQTT 验证协议与故障分支；界面层注入独立数据目录和内存凭据，验证模式切换、包过滤、版本展示、队列和重启恢复，不读写用户真实凭据。相关回归陷阱见 [[IPM接入时的静态测试迁移记录]]。
