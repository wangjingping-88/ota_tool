# OTA 状态查询延迟误判排查记录

## 现象

EcoLink 循环升级期间，桌面工具提示 `cmd=8` 状态查询连续三次无响应并结束当前任务，但 Gateway 下游升级仍在正常执行，稍后还能在 MQTT RX 中看到状态消息。

## 根因

工具原来的状态轮询策略存在两个问题：

1. 单次查询只等待 3 秒，连续三次超时后直接把 OTA 任务标记为失败。
2. 工具只接受当前正在等待的 `query_seq`；Broker 或 Gateway 延迟送达的旧查询响应即使属于当前 `task_seq` 和 `session_id`，也会被忽略。

现场日志中，工具在 17:01:40、17:01:48、17:02:01 发出的查询直到 17:02:17～17:02:19 才到达 Gateway。工具已于 17:02:04 提前结束轮询，而 Gateway 随后正常完成 5/5 个 Node 的升级，因此属于工具端误判。

## 修复

- 默认单次状态响应等待时间由 3 秒调整为 8 秒。
- 连续三次无响应时仅提示“状态暂不可用”，不再判定升级失败。
- 后续查询采用 5、10、20、30 秒封顶的退避间隔持续执行，最终仍由 Gateway 终态、用户取消或任务总超时决定结果。
- 为当前任务保留最近 16 个已发出的查询序号；只要 `task_seq`、`session_id` 匹配，就接受尚未处理的延迟响应。
- 接收到任一有效状态后清零连续超时计数并恢复正常轮询。

## 验证方法

冒烟测试模拟第一个查询已经超时、第二个查询正在等待时，注入第一个查询的延迟成功响应，验证任务能够恢复并识别成功终态。同时验证完全无响应时，第四次及后续查询仍会继续发送，任务不会被误判为失败。
