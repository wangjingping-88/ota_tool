# OTA 桌面工具智能化改造方案

相关文档：[[EcoLink OTA设计文档]]、[[OTA桌面测试工具设计方案]]、[[Gateway OTA状态查询与设备自动发现实施交接]]。

## 1. 改造目标

本次改造通过统一四端固件标识、版本号和发现协议，使桌面工具能够自动识别镜像、自动命名 Patch、自动筛选设备，并在升级请求发出前完成类型、版本、大小、目标范围和网络条件检查，尽量把配置错误拦截在最上层。

涉及范围：

- Node、Async、Sync、Gateway 四端固件镜像元数据。
- Gateway、Sync、Async、Node 之间的 OTA 协议和设备发现数据。
- 桌面工具的 PATCH 中心、升级任务和系统设置页面。
- Patch 元数据、Patch 门限、升级前检查和 256 Node 展示能力。

## 2. 兼容性边界

> [!IMPORTANT]
> 当前仍处于联调阶段，除旧镜像已经存在的 `eco[type]` 标识外，不保留其他兼容逻辑。发现协议、OTA 版本字段、Patch 元数据和桌面工具配置均直接切换到新格式，避免双协议、双字段和回退分支增加测试复杂度。

唯一保留的兼容场景：

- 旧镜像末尾存在有效的 `eco[type]`，但没有新增的版本字节时，桌面工具仍可识别设备类型。
- 此时版本显示为“未知”，用户必须在本次 Patch 制作时手动补充旧镜像版本。
- 补充后的版本只写入新生成的 Patch 元数据，不修改原始旧镜像。

明确不兼容：

- 不兼容旧版 Node/Extender 发现响应；缺少版本字段的响应直接判定为协议不匹配。
- 不兼容 OTA 协议中的字符串版本字段；四端统一使用单字节版本号。
- 不兼容没有元数据文件的历史 Patch；不得仅依赖文件名猜测类型和版本。
- 不迁移旧的 Patch 数据库记录、历史设备发现缓存或旧版配置结构。
- 不保留新旧协议自动降级、双解析或静默兜底逻辑。

## 3. 固件镜像标识统一

### 3.1 当前实现

Node、Async、Sync 已在镜像 `28 KiB` 边界前四字节写入标识：

| 地址 | 内容 |
| --- | --- |
| `0x6FFC` | `0x65`，字符 `e` |
| `0x6FFD` | `0x63`，字符 `c` |
| `0x6FFE` | `0x6F`，字符 `o` |
| `0x6FFF` | 设备类型 `type` |

代码中的实际字节为小写 ASCII `eco[type]`，文档和界面可统一称为 `ECO` 固件标识，但解析必须按实际字节匹配。Gateway 当前没有同等写入逻辑，需要补齐。

### 3.2 新格式

在原四字节标识前增加一个版本字节，保留原 `eco[type]` 的位置和内容：

| 地址 | 字段 | 长度 | 规则 |
| --- | --- | ---: | --- |
| `0x6FFB` | `version` | 1 字节 | 有效范围 `1～254` |
| `0x6FFC～0x6FFE` | magic | 3 字节 | 固定为 `0x65 0x63 0x6F` |
| `0x6FFF` | `type` | 1 字节 | 设备类型 `0～63` |

整体格式为：

```text
[version][e][c][o][type]
```

版本值 `0` 和 `255` 保留为无效值。新构建脚本必须显式写入 `0x6FFB`，不得依赖镜像填充值。

解析顺序：

1. 检查 `0x6FFC～0x6FFE` 是否为 `eco`。
2. 检查 `type` 是否处于合法范围并存在类型定义。
3. 若 `version` 为 `1～254`，按新格式返回类型和版本。
4. 若 `version` 为 `0`、`255` 或不能可信识别，则只按旧格式返回类型，版本标记为“未知”。
5. magic 或类型无效时拒绝导入，并提示“未识别到有效 ECO 固件标识”。

### 3.3 类型定义

四端和桌面工具必须共用同一份类型表，禁止分别维护含义不同的常量：

| 值 | 标识 | 中文名称 | Patch 文件名前缀 |
| ---: | --- | --- | --- |
| 0 | `SERVER` | 云平台服务器 | `server` |
| 1 | `EXTENDER_A` | 扩展器-异步 | `ext-a` |
| 2 | `EXTENDER_S` | 扩展器-同步 | `ext-s` |
| 3 | `ROOM_LIGHT` | 室内灯控 | `room-light` |
| 4 | `SWITCH` | 开关 | `switch` |
| 5 | `SOCKET` | 电源插座 | `socket` |
| 6 | `DTU` | DTU | `dtu` |
| 7 | `STREET_LIGHT` | 路灯控制器 | `street-light` |
| 8 | `GATEWAY` | 网关 | `gateway` |

Node Patch 按具体类型使用独立文件名前缀，防止相同版本方向的不同 Node 类型 Patch 在输出目录中互相覆盖；具体 Node 类型同时记录在 Patch 元数据中。工具继续兼容导入历史 `node` 前缀元数据，但新制作的 Patch 不再生成通用 `node` 前缀。当前各工程类型配置并不完全一致，实施时先抽取或生成共享类型定义，确保类型 0～8 在构建端、协议端和桌面工具端一一对应。

### 3.4 四端构建改造

- Node：沿用 `node_software_version` 的单字节校验和 `SOFTWARE_VERSION` 定义，将同一值写入镜像版本字节。
- Async：新增 `async_software_version` 构建参数，范围 `1～254`；移除 OTA 匹配所用的字符串版本。
- Sync：新增 `sync_software_version` 构建参数，范围 `1～254`；原 `DTU_VERSION` 字符串只允许用于产品信息和日志，不再参与 OTA 判断。
- Gateway：新增 `gateway_software_version` 构建参数以及镜像尾部标识写入逻辑，设备类型固定为 8。
- 四端运行时统一使用 `SOFTWARE_VERSION` 表示 OTA 数字版本；如需保留语义版本字符串，只用于展示，不能作为升级匹配依据。

构建时必须检查最终镜像长度至少覆盖 `0x6FFF`，写入后重新读取并校验五字节标识。构建日志输出类型、版本和五字节十六进制值，便于追踪产物。

## 4. OTA 协议版本统一

现有下游 OTA 协议中的 `old_version[16]`、`new_version[16]` 字符串改为：

```c
uint8_t old_version;
uint8_t new_version;
```

同时将 `DOWNSTREAM_OTA_PROTOCOL_VERSION` 从 2 升级到 3。Gateway、Sync、Async、Node 一次性同步升级，不保留 V2/V3 双解析。

MQTT JSON 中版本字段也改为数字：

```json
{
  "old_ver": 1,
  "new_ver": 2
}
```

字符串版本直接判定为请求格式错误。协议解析阶段统一验证版本范围 `1～254`，并在错误响应中区分“协议版本不匹配”“设备类型不匹配”和“底固件版本不匹配”。

## 5. 设备发现协议增强

### 5.1 Node 发现结果

Node 刷新结果新增一字节版本号，单条记录至少包含：

- Node ID。
- RSSI。
- 设备类型。
- 固件版本。
- 所属 Extender ID。

桌面工具的数据模型和持久化记录同步增加 `Version`。新协议响应必须带版本字段，缺失时直接提示固件协议版本过旧，不做旧格式猜测。

推荐显示格式：

```text
64654 · 电源插座（5）· v1 · -58 dBm
```

### 5.2 Extender 发现结果

Extender 刷新结果同步增加设备类型和版本，以便 Extender 升级也执行类型、底版本和目标版本检查。Extender 类型只允许 1 或 2。

### 5.3 256 Node 支持

协议已经允许每个 Extender 最多 256 个 Node，并按每页 64 个返回，共 4 页。桌面工具需要保证：

- 四页全部接收完成后再一次性替换列表，避免每页到达都触发布局重算。
- 按 `(ExtenderId, NodeId)` 去重，检查页码连续性和记录总数。
- 使用支持 UI 虚拟化的 `ListBox` 或 `DataGrid`，启用 `VirtualizingStackPanel` 和容器回收。
- 不再使用嵌套 `ItemsControl + WrapPanel` 一次创建全部控件。
- 提供类型筛选和 Node ID 搜索；筛选只影响显示，不改变未显示节点的选择状态。
- 列表更新和持久化批量执行，避免 256 次逐项通知阻塞界面。

## 6. PATCH 中心智能化

### 6.1 镜像导入

导入 A、B 镜像时自动读取五字节标识，并显示：

- 镜像类型和类型编号。
- 固件版本。
- 是否为旧 `eco[type]` 兼容镜像。
- 文件大小和 SHA-256。

制作前检查：

- A、B 镜像类型必须相同。
- A、B 版本必须有效且不同。
- 旧格式镜像只允许手动补充版本；补充前不能开始制作。
- 用户补充的版本必须处于 `1～254`，并在确认弹框中明确标记为人工输入。

### 6.2 自动命名

根据镜像类型和版本自动生成文件名：

```text
room-light-v1-to-v2.patch
switch-v1-to-v2.patch
socket-v1-to-v2.patch
dtu-v1-to-v2.patch
street-light-v1-to-v2.patch
ext-a-v1-to-v2.patch
ext-s-v1-to-v2.patch
gateway-v1-to-v2.patch
```

Node 的具体类型同时体现在文件名前缀和强制元数据中。正向、反向 Patch 分别根据输入方向生成，不允许用户编辑出与元数据矛盾的名称。

### 6.3 强制 Patch 元数据

每个 Patch 必须同时生成同名侧车文件，例如：

```text
socket-v1-to-v2.patch
socket-v1-to-v2.patch.json
```

建议字段：

```json
{
  "schema_version": 1,
  "patch_type": "socket",
  "device_type": 5,
  "old_version": 1,
  "new_version": 2,
  "patch_size": 17420,
  "patch_md5": "...",
  "patch_sha256": "...",
  "old_image_sha256": "...",
  "new_image_sha256": "...",
  "engine": "bsdiff_cmd.exe",
  "restore_verified": true,
  "created_at": "2026-08-19T10:00:00+08:00"
}
```

没有侧车文件、字段缺失、文件哈希不一致或 `restore_verified` 不为 `true` 的 Patch 禁止进入目录和升级任务。历史裸 Patch 不做兼容，必须重新导入 A、B 镜像生成。

### 6.4 Patch 还原验证

Patch 生成后先输出到临时目录，自动执行还原测试：

1. 使用 A 镜像和 Patch 还原出临时镜像。
2. 比较临时镜像与 B 镜像的长度和 SHA-256。
3. 读取还原镜像五字节标识，确认类型、版本与 B 镜像一致。
4. 全部通过后才移动到 Patch 目录并写入侧车元数据。
5. 任一检查失败时删除临时结果，不污染 Patch 目录。

## 7. Patch 门限配置

当前已确认的代码门限：

| Patch 类型 | 当前默认值 | 十进制 | 说明 |
| --- | ---: | ---: | --- |
| Node | `0xD000` | 53,248 B（52 KiB） | `NODE_OTA_PACKAGE_MAX_SIZE` |
| Extender-A | `0x2F000` | 192,512 B（188 KiB） | `ASYNC_OTA_PACKAGE_MAX_SIZE` |

在系统设置增加“Patch 大小门限”：

- 按 Patch 类型分别配置并持久化。
- 同时显示十六进制、字节数和 KiB，减少换算错误。
- 提供“恢复代码默认值”按钮。
- 默认值来自当前固件代码常量，不写散落在界面逻辑中；建议在构建或发布阶段生成一份桌面工具可读取的默认配置。
- Gateway、Extender-S 的默认值必须先从各自升级分区和校验代码确认，未确认前不得沿用其他类型门限。

生成 Patch 后立即校验大小。超过门限时不进入目录，并提示：

```text
Patch 大小 58.3 KiB，超过 Node 当前门限 52 KiB。
请减小版本跨度或采用分段升级，例如 v1 → v2 → v3。
```

桌面配置可编辑只用于跟随固件门限调整；修改时必须二次确认，界面明确提示“桌面门限大于设备实际门限仍会导致升级失败”。

## 8. 升级任务页面智能化

### 8.1 Node 类型与目标选择

- Node 类型下拉框只显示本次刷新实际发现的类型。
- 选择 Node Patch 后，根据元数据中的 `device_type` 自动选择并锁定对应类型。
- 只允许逐个勾选符合 Patch 类型的 Node，取消现有“全部选择/全部取消”按钮。
- 不符合类型的 Node 保持可见但禁用，显示不匹配原因，避免用户误以为设备丢失。
- 若当前发现结果不存在 Patch 所需类型，启动按钮置灰并给出明确原因。
- 用户选择的 Node 类型、版本必须与 Patch 的类型和底版本一致；任一不一致时禁止发送升级请求。

### 8.2 版本辅助选择

- 选择 Patch 后自动将旧版本、新版本带入升级参数，不允许手动输入与元数据不同的值。
- 已处于目标版本的设备默认禁用，并标记“无需升级”。
- 发现结果包含多个底版本时不自动拆分任务；要求用户按版本筛选，只选择同一底版本设备。
- 刷新后如果已选设备的版本或类型发生变化，自动取消该设备并提示原因。

### 8.3 循环升级

循环升级除通用检查外还必须满足：

- 已同时选择正向和反向 Patch。
- 两个 Patch 的 `device_type` 相同。
- 正向的 `old_version/new_version` 与反向的 `new_version/old_version` 完全互逆。
- 两个 Patch 均通过还原验证并未超过各自门限。

条件不满足时“启动循环升级”保持置灰，并在旁边显示第一条阻断原因。

## 9. 升级前检查

点击“启动单次升级”或“启动循环升级”后，先在本地完成全部检查，再立即弹出应用风格确认框。只有用户确认后才发送命令。

### 9.1 阻断项

| 类别 | 检查内容 |
| --- | --- |
| Patch 完整性 | Patch 和侧车文件存在，大小、MD5、SHA-256 与元数据一致，已通过还原验证 |
| 任务类型 | 升级类型与 Patch 类型一致；Node 具体类型与 `device_type` 一致 |
| 版本关系 | 设备当前版本等于 `old_version`，目标版本等于 `new_version`，两者不同 |
| 目标范围 | 至少选择一个目标；Extender、Node 数量不超过协议上限；ID 不重复 |
| 设备状态 | 类型和版本均已发现；未知版本不允许升级 |
| Patch 门限 | Patch 大小不超过当前类型门限 |
| MQTT | Broker 已连接，Gateway 主题已订阅，Gateway ID 合法 |
| HTTP | 文件可访问，Content-Length 正确，Range 请求返回 206，内容 MD5 一致 |
| 任务互斥 | Gateway 和桌面工具均不存在未结束的 OTA 任务 |
| 循环关系 | 正反 Patch 类型一致、版本互逆、均通过完整性检查 |

### 9.2 警告项

以下项目只警告，不默认阻断：

- RSSI 低于系统设置阈值。
- 设备发现结果超过用户配置的有效时间。
- 用户为旧 `eco[type]` 镜像手动补充了版本。
- 目标数量较大，预计任务耗时较长。

确认框按“基本信息、目标统计、阻断项、警告项”分区显示。存在阻断项时只提供“返回修改”，不存在阻断项时才显示“确认启动”。

## 10. 配置与数据模型

### 10.1 系统设置新增项

- 各设备类型 Patch 大小门限。
- 发现结果有效时间。
- 低 RSSI 警告阈值。
- 是否显示不匹配设备，默认显示但禁用。

### 10.2 核心数据模型

建议引入统一模型：

```text
FirmwareIdentity
├── DeviceType
├── DeviceTypeName
├── Version
├── IsLegacyEcoMarker
└── SourcePath

DiscoveredDevice
├── DeviceId
├── ParentExtenderId
├── DeviceType
├── Version
├── Rssi
└── LastSeenAt

PatchDescriptor
├── PatchType
├── DeviceType
├── OldVersion
├── NewVersion
├── Size/MD5/SHA256
├── Old/NewImageSHA256
└── RestoreVerified
```

业务校验只依赖这些强类型模型，不再从界面文本、文件名或日志字符串反向推断关键参数。

## 11. 实施顺序

### 第一阶段：固件元数据与版本统一

1. 固化共享类型表和版本范围。
2. 为 Node、Async、Sync、Gateway 统一构建参数和 `SOFTWARE_VERSION`。
3. 四端统一写入 `[version][eco][type]`。
4. 增加构建后镜像标识校验。

### 第二阶段：协议一次性切换

1. OTA 协议升级至 V3，字符串版本改为单字节。
2. Node 和 Extender 发现记录增加版本字段。
3. Gateway、Sync、Async、Node 同步更新并完成协议单元测试。
4. 删除旧协议解析和兼容分支。

### 第三阶段：PATCH 中心改造

1. 实现新旧镜像标识解析，其中仅保留旧 `eco[type]` 识别。
2. 实现自动命名和强制侧车元数据。
3. 接入 Patch 还原验证与哈希校验。
4. 实现按类型配置的 Patch 门限。

### 第四阶段：升级任务智能化

1. 发现结果按类型和版本建模、持久化。
2. Node 类型动态列表、Patch 联动和不匹配设备禁用。
3. 移除 Node 全选按钮，增加版本筛选和搜索。
4. 完成 256 Node 虚拟化和分页结果校验。
5. 实现统一升级前检查与应用风格确认框。

### 第五阶段：联调与清理

1. 四端固件与桌面工具统一升级后进行单次、循环、取消、失败重试测试。
2. 覆盖 Node 五种类型、Extender-A、Extender-S 和 Gateway。
3. 验证旧 `eco[type]` 镜像只能走“识别类型 + 手动补版本”路径。
4. 删除所有临时兼容代码、测试开关和重复配置。

## 12. 验收标准

- 四端新镜像均能从固定地址读出正确的类型和单字节版本。
- 旧 `eco[type]` 镜像可以识别类型，但必须手动补充版本后才能制作 Patch。
- 桌面工具导入两份新镜像后无需手填类型、版本和 Patch 名称。
- Patch 必须通过还原验证、哈希校验和大小门限后才进入目录。
- 没有有效侧车元数据的 Patch 无法发起升级。
- Node/Extender 刷新结果均包含版本；缺失版本的数据明确报协议不匹配。
- 选择 Patch 后只允许选择类型和底版本匹配的设备。
- 每个 Extender 展示 256 个 Node 时，滚动、筛选和选择无明显卡顿，分页无丢失或重复。
- 所有阻断错误均在发送 MQTT 升级命令前提示。
- 循环升级只能使用类型一致且版本互逆的正反 Patch。
- 代码中不存在除旧镜像 `eco[type]` 识别之外的新旧格式兼容分支。

## 13. 实施注意事项

> [!WARNING]
> 固件协议和发现记录不做兼容，因此四端固件与桌面工具必须作为同一套基线同步发布。任一端未更新时应明确报“协议版本不匹配”，不能继续执行升级。

- 类型、版本、门限只保留一个权威来源，其他语言和工程通过生成文件或受控复制获取。
- 固件版本是单字节升级匹配字段，不等同于面向用户的语义版本或 Git 标签。
- 版本号到达 254 前必须规划下一代镜像元数据格式，禁止回绕后继续比较。
- 手动修改 Patch 门限不会改变设备端能力，联调时应同时记录桌面设置和固件常量。
- Patch 目录写入采用“临时文件生成、完整校验、原子移动”的流程，避免中断留下可选但不完整的 Patch。
